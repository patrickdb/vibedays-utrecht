# Database

## Approach

- SQLite through `@libsql/client`, queried with Drizzle ORM. `DATABASE_URL` (see `.env.example`, default `file:./data/app.db`) is the only connection setting; `data/` is gitignored.
- `lib/db.ts` is the only module that opens the database and exports the Drizzle instance. It imports `server-only`, so client components cannot pull it in. Everything else imports `db` from there.
- Schema lives in `lib/schema.ts` and is currently empty on purpose: todo tables come with the todo architecture, auth tables with authentication.
- Migrations are SQL files generated by drizzle-kit into `drizzle/` and committed. Never edit the database by hand or use `drizzle-kit push`.

## Commands

- `npm run db:generate` writes a migration for schema changes ("nothing to migrate" is normal while the schema is empty).
- `npm run db:migrate` applies pending migrations to `DATABASE_URL`; it also creates the database file.
- `npm run db:reset` deletes the file behind `DATABASE_URL` (refuses non-`file:` URLs) and migrates a fresh one.

## Versions and gotchas

- `drizzle-orm` and `drizzle-kit` are on the v1 release candidate (`@rc`), because that is what the docs describe; npm `latest` is the old 0.x line with a different API. Install new Drizzle packages with `@rc`.
- `drizzle.config.ts` uses `dialect: "turso"` (the libsql dialect, which also accepts `file:` URLs). drizzle-kit does not read `.env`, so the config loads it with `process.loadEnvFile`; variables already in the environment win. The same applies to `scripts/db-reset.mjs`.
- v1 `drizzle()` has no `schema` option (relations replaced it); pass `relations` once tables exist.
- `lib/db.ts` throws at import time when `DATABASE_URL` is unset. Once a page imports it, `next build` needs `DATABASE_URL` too (CI writes it into `.env`).
- Tests never touch `data/app.db`: the Vitest test (`tests/unit/db.test.ts`) migrates a temp file and mocks `server-only` (which throws outside a React Server Components build); Playwright runs `db:migrate` against its own temp file before starting the server (see [testing.md](testing.md)).
- On Windows the libsql client keeps a SQLite file locked until the process exits, so tests cannot delete their temp database in `afterAll`.
